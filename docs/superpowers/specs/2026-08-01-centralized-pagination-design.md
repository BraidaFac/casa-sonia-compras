# Centralized Pagination & MySQL Sort Buffer Fix

**Date:** 2026-08-01
**Status:** Approved

## Problem

`GET /api/inventario` triggers MariaDB error `1038: Out of sort memory` because the
`findMany` query selects `articles: true` — loading the full JSON blob for every inventory
row — while also applying `orderBy: { createdAt: "desc" }`. MariaDB must hold all JSON
blobs in the sort buffer simultaneously, which exceeds `sort_buffer_size` as inventories grow.

Additionally, both list pages (`/inventario` and `/odoo-orders`) duplicate offset/limit
pagination state and UI with different patterns (React Query vs `useEffect`).

## Scope

- Fix the sort buffer error at the root cause (DB schema + query).
- Centralize pagination state and UI across both list pages.
- Migrate `/odoo-orders` from `useEffect` to React Query for consistency.
- **Out of scope:** Paginating articles within a single inventory detail (`/inventario/[id]`).
  The detail uses `findUnique` by PK — no sort, no buffer issue.

## 1. Schema Migration

Add a denormalized `article_count` integer column to `inventories`.

```prisma
model Inventory {
  // ... existing fields ...
  articles            Json            @default("[]")
  articleCount        Int             @default(0) @map("article_count")
}
```

Migration SQL (generated by Prisma, then customized with backfill):

```sql
ALTER TABLE inventories ADD COLUMN article_count INT NOT NULL DEFAULT 0;

UPDATE inventories
SET article_count = JSON_LENGTH(articles)
WHERE JSON_VALID(articles);
```

Backfill runs in the same migration — no downtime, no inconsistent state.

## 2. API Changes

### `GET /api/inventario`

Remove `articles: true` from the `findMany` select. Add `articleCount: true`.

```typescript
select: {
  id: true,
  status: true,
  warehouseId: true,
  warehouseName: true,
  name: true,
  countDate: true,
  accountingDate: true,
  articleCount: true,   // replaces: articles: true
  odooRef: true,
  errorDetail: true,
  createdAt: true,
  updatedAt: true,
  createdBy: { select: { name: true } },
},
```

In the summary map, replace `Array.isArray(articles) ? articles.length : 0` with `inv.articleCount`.

### `PATCH /api/inventario/[id]`

When `body.articles` is present, sync `articleCount` in the same Prisma update:

```typescript
if (body.articles !== undefined) {
  data.articles = body.articles as unknown as object[];
  data.articleCount = body.articles.length;
}
```

Single atomic update — no race condition.

### `LocalInventorySummary` type

No interface change. `articleCount: number` already exists; it now comes from the DB
column instead of being computed client-side.

### Edge cases

| Scenario | Behavior |
|----------|----------|
| `PATCH` without `body.articles` (name/status change only) | `articleCount` untouched, stays correct |
| `PATCH` with `body.articles = []` | `articleCount = 0`, correct |
| Invalid JSON in `articles` at migration time | Skipped by `WHERE JSON_VALID(articles)`, stays `0` |

## 3. Centralized Pagination

### `usePagination` hook — `src/hooks/usePagination.ts`

Manages offset/limit/page state. All derived values computed from `offset`.

```typescript
interface UsePaginationOptions {
  pageSize?: number;  // default 30
  total: number;
}

interface UsePaginationReturn {
  offset: number;
  limit: number;
  page: number;       // 1-based display
  totalPages: number;
  hasPrev: boolean;
  hasNext: boolean;
  goNext: () => void;
  goPrev: () => void;
  goToPage: (p: number) => void;
  reset: () => void;  // returns to page 1 — call on filter change
}
```

Internal state: single `offset` integer. Everything else is derived.

### `PaginationControls` component — `src/components/ui/PaginationControls.tsx`

Replaces duplicated JSX in both list pages.

```typescript
interface PaginationControlsProps {
  total: number;
  offset: number;
  limit: number;
  hasPrev: boolean;
  hasNext: boolean;
  onPrev: () => void;
  onNext: () => void;
  entityLabel: string;  // e.g. "inventarios", "órdenes"
}
```

Renders: total count text + Anterior/Siguiente buttons. Both buttons disabled when
`total = 0`. Component always renders (no conditional hide) so layout stays stable.

### Edge cases

| Scenario | Behavior |
|----------|----------|
| `total = 0` | Both buttons disabled, component renders |
| Filter changes while on page 3 | Caller invokes `reset()` in filter `onChange` → offset = 0 before next fetch |
| `total` undefined (first load) | Hook receives `0`, buttons disabled, no crash |

## 4. Orders → React Query

### New hook — `src/hooks/useOdooOrders.ts`

```typescript
interface OdooOrdersParams {
  supplierId?: number;
  state?: string;
  dateFrom?: string;   // YYYY-MM-DD
  dateTo?: string;     // YYYY-MM-DD
  limit?: number;
  offset?: number;
}

export function useOdooOrders(params: OdooOrdersParams) {
  return useQuery({
    queryKey: ["odoo-orders", params],
    queryFn: () => fetchOdooOrders(params),
    staleTime: 60_000,   // 1 min — Odoo state can change externally
  });
}
```

`staleTime: 60_000` (not `Infinity`) — Odoo orders can change state externally.

### `/odoo-orders/page.tsx` changes

Remove: `useState<OCSummary[]>`, `useState(loading)`, `useCallback(fetchOrders)`, `useEffect`.

Replace with:

```typescript
const pagination = usePagination({ total: data?.total ?? 0 });

const params: OdooOrdersParams = {
  supplierId: supplier?.id,
  state: stateFilter ?? undefined,
  dateFrom: dateFrom?.toISOString().split("T")[0],
  dateTo: dateTo?.toISOString().split("T")[0],
  limit: pagination.limit,
  offset: pagination.offset,
};

const { data, isLoading } = useOdooOrders(params);
```

Each filter change produces a new `queryKey` → automatic fetch. No `useEffect`, no
`useCallback`. Filter `onChange` handlers call `pagination.reset()` before updating state.

### Edge cases

| Scenario | Behavior |
|----------|----------|
| Rapid filter changes | React Query ignores stale responses, shows latest |
| Odoo API error | `isError` available for display (currently silenced) |
| `supplier` null → `supplierId` undefined | URLSearchParams skips undefined, API ignores missing param |
